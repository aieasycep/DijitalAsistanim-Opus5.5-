# Dijital Asistan: Security

This file is the operational security summary of the repository. The design, threat model and control
specifications live in [SECURITY_AND_PRIVACY_PLAN.md](SECURITY_AND_PRIVACY_PLAN.md); this file records
how each threat is verified in code and what risk remains.

## Threat-model verification checklist (M§113, M§114; IMPLEMENTATION_PLAN T-11.05)

Every threat of [SECURITY_AND_PRIVACY_PLAN §2](SECURITY_AND_PRIVACY_PLAN.md#2-threat-model) listed in
M§113 has at least one test that attacks the merged code path (not a re-implementation of it):

- **Edge suite:** `supabase/functions/tests/security/*.test.ts`. It runs in `pnpm functions:test`
  (`C-FN`), which has no network permission, so provider HTTP is always a stub.
- **SQL suite:** `supabase/tests/database/300_threats_*.test.sql`. It runs in tier C
  (`bash scripts/db/tier-c.sh`, `C-DB`) next to the pgTAP suites it extends.

Reading the table:

- **Controls** name the control sections of the plan.
- **Verified by** names the new threat tests first, then the existing suites they build on.
- **Residual risk** is what remains after the controls, as the plan rates it, plus anything the tests
  showed.

### Findings fixed by this suite

1. **The logger did not deny OAuth flow secrets by key (THR-01, CTL-3.14).** `code`, `code_verifier`,
   `state`, `client_secret`, `set-cookie` and `signature` were missing from the key denylist, and so
   were the R-07 values `completion_code` and `device_nonce`. A 43-character PKCE verifier, state or
   completion code is shorter than the generic 48-character scrubber, so logging one of them under
   its own name would have written it in clear.
   - Fix: the keys are now denied in `_shared/logging/logger.ts`.
   - Follow-up: the six warnings in `services/integrations/connect.ts` and `disconnect.ts` that logged
     a provider error code as `code` now use `error_code`, so they stay readable.
   - Test: `tests/security/token-theft.test.ts`.
2. **Half of an A↔B referral loop was rewarded (THR-15).** The loop walk of
   `private.referral_evaluation_context` skipped rejected referrals. Once JOB-25 rejected the first
   leg as a loop, the mirror leg no longer saw the cycle and both sides of it were rewarded.
   - Fix: migration `20260924002700_referral_loop_edges.sql` keeps legs that were rejected as `loop`
     in the walk. The in-memory repository in `_shared/testing/business.ts` mirrors the change.
   - Tests: `tests/security/referral-abuse.test.ts` and `300_threats_writes.test.sql`.
